GIÁO TRÌNH CHUYÊN SÂU AUTOSAR CAN RX STACK

Từ CAN Bus đến Com_ReceiveSignal(), qua 4 tầng BSW

Tài liệu này bám sát đúng code demo trong repository hiện tại. Mục tiêu không chỉ là mô tả "có các lớp AUTOSAR", mà là chỉ rõ dữ liệu đang nằm ở đâu, ai gọi ai, và cuối cùng Application lấy được giá trị Signal bằng cách nào.

Một câu chốt bản chất của luồng RX: Ứng dụng không trực tiếp đọc CAN frame. Khi CAN frame đến phần cứng, chuỗi callback tự động chạy từ Can Driver → CanIf → PduR → COM để copy dữ liệu vào shadow buffer. Sau đó, ứng dụng chỉ việc gọi Com_ReceiveSignal() để đọc Signal từ buffer đó.

1. Mục tiêu học tập và bức tranh toàn cục

Sau khi học xong tài liệu này, người học cần trả lời được các câu hỏi sau mà không còn mơ hồ:

  • Tại sao Application không gọi CAN_Receive() trực tiếp mà phải qua 4 tầng BSW?
  • Dữ liệu tồn tại lần lượt ở những bộ đệm nào từ khi nhận CAN frame đến khi Application đọc Signal?
  • Sự khác nhau giữa CAN ID (0x181), PDU ID (5) và Signal ID (17) là gì?
  • Vai trò của Can, CanIf, PduR và Com khác nhau ở chỗ nào?
  • Vì sao luồng RX chia làm 2 giai đoạn riêng biệt (Nhận & Lưu vs Đọc Signal)?

Chuỗi đi đúng của dữ liệu trong luồng RX:
CAN Bus → bxCAN FIFO → Can_MainFunction_Read() / ISR → CanIf_RxIndication() → PduR_CanIfRxIndication() → Com_RxIndication() → Shadow Buffer → Com_ReceiveSignal() → Application

2. CAN là gì ở góc nhìn kỹ thuật hệ thống

2.1 Bản chất của CAN

CAN (Controller Area Network) là mạng truyền thông chính trong ô tô, dùng cho các hệ thống yêu cầu độ tin cậy cao và tốc độ trung bình như động cơ, phanh, hộp số.

Đặc tínhCANÝ nghĩa trong demo
Cấu trúc busMulti-master, event-drivenBất kỳ Node nào cũng có thể gửi frame bất cứ lúc nào.
Cơ chế truy cập busCSMA/CA – Arbitration theo IDID càng nhỏ, ưu tiên càng cao.
Tầng vật lýDifferential 2-wire (CAN_H, CAN_L)Chân PA11 (RX) và PA12 (TX) nối qua transceiver.
Tốc độ500 kbps (demo này)Prescaler=4, BS1=11, BS2=6 trên APB1 36MHz.
Khung dữ liệuSOF + Arbitration + Control + Data + CRC + ACK + EOFbxCAN hardware tự xử lý; phần mềm chỉ đọc payload từ FIFO.

3. Kiến trúc AUTOSAR COM Stack và vị trí luồng RX

3.1 Bốn module trên luồng RX

Trên luồng nhận (RX), dữ liệu đi từ dưới lên trên. Mỗi tầng có một vai trò rõ ràng:

TầngModuleFileNhiệm vụ chính trong luồng RX

3.2 Hai khái niệm cốt lõi: Signal vs PDU

Khái niệmMô tảVí dụ cụ thể trong demo

I-PDUInteraction Layer PDU — gói byte chứa nhiều SignalEngineStatus = 3 byte = [RPM_Hi, RPM_Lo, Temp]
L-PDULower Layer PDU — tương đương CAN frame trên busCAN ID 0x181, DLC=3, Data=[0x04,0x1A,0x46]

3.3 Tại sao cần 4 tầng?

ModuleCâu hỏiTrả lời
Can DriverTại sao không để App đọc FIFO trực tiếp?Vì MCAL trừu tượng hóa phần cứng. Đổi MCU chỉ cần đổi driver, code trên không thay đổi.
CanIfTại sao cần CanIf khi đã có Can Driver?Vì CAN chỉ biết CAN ID (0x181), nhưng tầng trên dùng PDU ID (5). CanIf dịch giữa 2 thế giới.
PduRTại sao không từ CanIf gọi thẳng COM?Vì PDU có thể đi đến COM (data thường) hoặc DCM (chẩn đoán). PduR là "bưu điện" phân phối.
COMTại sao cần COM khi PduR đã có data?Vì PduR chỉ biết PDU (mảng byte). COM biết Signal — nơi unpack byte thành giá trị có ý nghĩa.
Điểm rất dễ nhầm: Luồng RX chia làm 2 giai đoạn riêng biệt không đồng bộ:
Giai đoạn 1 (Nhận & Lưu): ISR hoặc Polling → chuỗi callback → copy vào shadow buffer. Xảy ra bất cứ lúc nào có frame.
Giai đoạn 2 (Đọc Signal): App chủ động gọi Com_ReceiveSignal() khi cần. Xảy ra trong main loop.

5. Luồng thực thi đầy đủ từ CAN Bus đến Application

5.1 Giai đoạn khởi tạo

void BSW_Init_RX(void) {
    Can_Init();                // 1. Cấu hình bxCAN: GPIO, filter, bit timing, NVIC
    CanIf_Init();              // 2. Đánh dấu CanIf sẵn sàng
    PduR_Init(&PduR_ConfigPB); // 3. Load bảng route, bật routing
    Com_Init();                // 4. Xóa toàn bộ shadow buffer về 0
}
Thứ tự khởi tạo rất quan trọng: Phải init từ dưới lên trên (Can → CanIf → PduR → COM), vì tầng trên phụ thuộc vào tầng dưới. Nếu đảo ngược, callback chain sẽ gọi vào module chưa sẵn sàng.

5.2 Tầng 1 — Can Driver: Đọc frame từ phần cứng

CAN Driver hỗ trợ 2 cơ chế nhận song song:

Cơ chếHàmKhi nào chạyƯu điểm
Interrupt (ISR)USB_LP_CAN1_RX0_IRQHandler()Tức thì khi frame vào FIFO0Độ trễ thấp nhất
PollingCan_MainFunction_Read()Định kỳ từ main loopBackup, đảm bảo không bỏ sót
 
// Can.c — ISR nhận CAN frame (dòng 404-417)
void USB_LP_CAN1_RX0_IRQHandler(void)
{
    CanRxMsg rxMsg;        // Cấu trúc SPL
    PduInfoType pduInfo;   // Cấu trúc AUTOSAR

    while (CAN_MessagePending(CAN_PERIPH, CAN_FIFO0) > 0) {
        CAN_Receive(CAN_PERIPH, CAN_FIFO0, &rxMsg);  // Đọc từ FIFO HW

        pduInfo.SduDataPtr = rxMsg.Data;    // Con trỏ payload
        pduInfo.SduLength  = rxMsg.DLC;     // Số byte

        CanIf_RxIndication(rxMsg.StdId, &pduInfo);  // ← Gọi lên CanIf
    }
}

5.3 Tầng 2 — CanIf: Dịch CAN ID → PDU ID

// CanIf.c — Routing theo CAN ID (dòng 162-178)
void CanIf_RxIndication(Can_IdType canId, const PduInfoType* PduInfoPtr)
{
    if (PduInfoPtr == NULL) return;

    if (canId == 0x7DF || canId == 0x7E8) {
        CanTp_RxIndication(0, PduInfoPtr);           // Diagnostic → CanTp
    }
    else if (canId == 0x181) {
        PduR_CanIfRxIndication(                       // EngineStatus → PduR
            CanIfConf_Pdu_EngineStatus, PduInfoPtr);  //   PDU ID = 5
    }
}
Điểm mấu chốt của CanIf: Phần cứng CAN chỉ biết CAN ID (0x181). Tầng trên (PduR, COM) chỉ biết PDU ID (5). CanIf là nơi duy nhất thực hiện việc dịch giữa 2 thế giới ID này.

5.4 Tầng 3 — PduR: Tra bảng route, chuyển đến COM

// PduR.c — RX callback (dòng 182-194)
void PduR_CanIfRxIndication(PduIdType CanIfRxPduId, const PduInfoType* PduInfoPtr)
{
    if (s_State == PDUR_UNINIT || !s_RoutingEnabled) return;
    if (s_Cfg->CanIfRxRoutingTable == NULL) return;

    // Tra bảng: SrcPduId=5 → DstPduId=5
    int32_t idx = prv_find_callback_route(
        s_Cfg->CanIfRxRoutingTable,
        PDUR_NUM_CANIF_RX_ROUTES,   // = 1
        CanIfRxPduId);              // = 5

    if (idx >= 0) {
        PduIdType comPduId = s_Cfg->CanIfRxRoutingTable[idx].DstPduId;
        Com_RxIndication(comPduId, PduInfoPtr);   // ← Gọi lên COM
    }
}

5.5 Tầng 4 — COM: Lưu vào shadow buffer

// Com.c — RX Indication (dòng 302-318)
void Com_RxIndication(PduIdType ComRxPduId, const PduInfoType* PduInfoPtr)
{
    PduLengthType len = 0u;
    Com_PduDirection_e dir = COM_PDU_DIR_TX;
    uint8* buf = prv_get_ipdu_buf(ComRxPduId, &len, &dir);

    if ((buf != NULL) && (dir == COM_PDU_DIR_RX)) {
        PduLengthType copyLen = (PduInfoPtr->SduLength < len)
                                 ? PduInfoPtr->SduLength : len;
        memcpy(buf, PduInfoPtr->SduDataPtr, copyLen);  // ← Copy vào buffer!
    }
}
Trước Com_RxIndication(): Com_IpduBuf[5] = [0x00, 0x00, 0x00]
Sau Com_RxIndication(): Com_IpduBuf[5] = [0x04, 0x1A, 0x46]

RPM=0x041A Temp=0x46

5.6 Application: Đọc Signal từ buffer

// Com.c — ReceiveSignal (dòng 254-296)
uint8 Com_ReceiveSignal(Com_SignalIdType SignalId, void* SignalDataPtr)
{
    const Com_SignalCfgType* cfg = &Com_SignalCfg[SignalId];
    uint8* ipdu = prv_get_ipdu_buf(cfg->PduId, &ipduLen, &dir);

    // Kiểm tra hướng phải là RX
    if (dir != COM_PDU_DIR_RX) return COM_SERVICE_NOT_AVAILABLE;

    switch (cfg->bitLength) {
        case 16u:
            *(uint16*)SignalDataPtr = get_u16(ipdu, cfg->byteIndex);  // Big Endian
            break;
        case 8u:
            *(uint8*)SignalDataPtr = get_u8(ipdu, cfg->byteIndex);
            break;
        // ...
    }
    return E_OK;
}
Hàm unpack 16-bit Big Endian: 
static inline uint16 get_u16(const uint8* src, uint16 byteIndex) {
    return (uint16)(((uint16)src[byteIndex] << 8) | (uint16)src[byteIndex + 1]);
}
// Ví dụ: get_u16([0x04, 0x1A, 0x46], 0) = (0x04 << 8) | 0x1A = 0x041A = 1050

6. Phân tích ở mức byte/bit: Pack và Unpack Signal

6.1 Phía TX: Com_SendSignal pack Signal vào buffer

Node TX gọi Com_SendSignal(ComSig_Engine_RPM, &rpm) với rpm = 1050:

put_u16(buf, 0, 1050)
→ buf[0] = (uint8)(1050 >> 8) = (uint8)(0x041A >> 8) = 0x04
→ buf[1] = (uint8)(1050 & 0xFF) = (uint8)(0x041A & FF) = 0x1A

Node TX gọi Com_SendSignal(ComSig_Engine_Temp, &temp) với temp = 70:

put_u8(buf, 2, 70)
→ buf[2] = 0x46

Kết quả buffer I-PDU trước khi gửi: [0x04, 0x1A, 0x46]

6.2 Phía RX: Com_ReceiveSignal unpack buffer ra Signal

SignalHàm unpackTính toánKết quả
Engine_RPMget_u16(buf, 0)(0x04 << 8) | 0x1A = 0x041A1050
Engine_Tempget_u8(buf, 2)0x4670

11. Các điểm dễ nhầm và kết luận kỹ thuật

11.1 Năm điểm dễ nhầm nhất

  • Com_ReceiveSignal() không kích hoạt việc nhận. Nó chỉ đọc từ buffer đã có sẵn. Việc nhận xảy ra ở chuỗi callback ISR/Polling.
  • CAN ID ≠ PDU ID ≠ Signal ID. Trong demo trùng nhau (đều = 5) là do thiết kế đơn giản, nhưng trong hệ thống thật chúng khác nhau.
  • Shadow buffer ghi đè không có lock. Demo không dùng mutex — nếu ISR đang copy mà App đang đọc, có thể đọc dữ liệu "nửa cũ nửa mới". Production code cần SchM critical section.
  • Com_SendSignal() chỉ dành cho TX, Com_ReceiveSignal() chỉ cho RX. Nếu gọi sai hướng, hàm trả về COM_SERVICE_NOT_AVAILABLE.
  • ISR và Polling cùng gọi CanIf_RxIndication(). Chúng không xung đột vì CAN_Receive() dequeue frame khỏi FIFO — mỗi frame chỉ được xử lý một lần duy nhất.

11.2 Kết luận cuối cùng

Điều quan trọng nhất để hiểu CAN RX trong AUTOSAR Classic là: Application không bao giờ tiếp xúc trực tiếp với phần cứng CAN. Thay vào đó:

  • Can Driver đọc frame từ FIFO phần cứng và chuyển thành cấu trúc phần mềm.
  • CanIf dịch CAN ID thành PDU ID — cầu nối giữa thế giới phần cứng và phần mềm.
  • PduR định tuyến PDU đến đúng module đích (COM cho data, DCM cho diagnostic).
  • COM lưu payload vào shadow buffer và unpack thành Signal khi App yêu cầu.

Nắm được chuỗi này thì việc đọc tiếp các chủ đề nâng cao như COM notification callback, signal gateway, deadline monitoring hay tích hợp với OS task sẽ dễ hơn rất nhiều.
